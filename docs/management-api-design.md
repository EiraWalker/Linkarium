# 收藏库管理 API 设计访谈

日期：2026-10-11。状态：用户已确认剩余使用方式并要求生成文档；已整理为[实施规格](management-api-spec.md)，尚未开始实现。

已发布：[GitHub Issue #1](https://github.com/EiraWalker/Linkarium/issues/1)，标签 `ready-for-agent`。

## 目标与已确认决定

让之后的本机 Agent 和脚本通过稳定管理 API 操作收藏库。用户已确认：

- 仅供本机调用。
- 首版覆盖链接、文件夹、标签、备注、后台任务、快照和 AI 分类。
- 鉴权复用软件密码登录与会话，不引入独立管理 Token。
- 交付 API、轻量 HTTP 命令行工具和可供后续 Agent 使用的 Skill。
- 重复添加时复用同级同名目录和已有链接；明确指定目标目录时移动已有链接。标题、备注和标签只修改明确提供的字段，省略字段保持原值。
- 提供范围内的删除操作：收藏、文件夹及其内容、标签和快照历史；沿用删除影响预览及提交机制。用户明确要求删除后，Agent 可完成预览和提交。
- 后台任务提供查询、重试和取消。
- AI 相关调用向后台提交分类任务，等待 AI 生成结果供审批；不把生成结果当作已批准或已执行的分类。
- 账号密码以明文保存在本地配置，会话失效后自动重新登录，并提供清除凭据命令；用户已明确取消 Windows 加密凭据保存功能。
- 扩展后端 HTTP API，让目录复用、收藏添加或更新与可靠重试成为服务端能力，CLI 和 Skill 通过 HTTP 调用。
- AI 待审批结果由用户在现有网页校对和审批；本次管理工具提供提交、查询、等待和获取建议，不提供确认或驳回命令。
- 范围边界见 [ADR 0008](adr/0008-local-management-api-scope.md)。

这些是设计约定，不是对当前收藏库执行移动、删除或分类的授权。

## 已核实的现状

- `/api/v1` 已有上述业务操作，当前使用固定 owner 的网页登录会话和 CSRF 校验；尚无专用管理 token 鉴权。
- 已有 revision 冲突校验、删除影响预览、异步任务查询和部分操作的幂等机制。
- 收藏按规范化 URL 去重；再次添加已有 URL 返回旧记录，不会按新请求自动更新目录或标题。
- 同级同名文件夹创建会返回冲突；文件夹和标签创建尚未统一接入幂等机制。
- 启动端口可能自动递增；未来调用入口需要可靠定位当前服务。
- 已有 API 契约和 OpenAPI，但部分机器契约较粗，没有通用 HTTP 管理客户端。

依据：`backend/config/api.py`、`backend/library/catalog.py`、`scripts/start.ps1`、`scripts/export-openapi.py` 与 `docs/api-contract.md` 的只读检查。

## 访谈收敛

用户要求生成规格文档，并在测试方案核对时明确修订：无需 Windows 凭据保存，账号密码直接以明文保存于本地，扩展后端 HTTP API。网页审批和其余已确认范围继续保留。用户授权在项目没有远程仓库时新建私有仓库，现使用 EiraWalker/Linkarium 作为 issue tracker，标签为 ready-for-agent。技术落地约定和测试验收建议集中记录在实施规格中；尚未实现功能代码。

## 密码登录的范围说明

当前软件使用固定 owner 的会话。复用密码登录不会自动产生一套更窄的服务端权限；本次管理工具只交付已选功能，现有网页登录能力保持其原有语义。

## 实施方向

扩展现有后端 HTTP API，复用业务校验并补齐目录确保存在、收藏添加或更新及请求幂等；由客户端读取本地明文账号密码并处理登录、会话及 CSRF。补充稳定服务定位和准确接口说明，具体契约、实现约定、范围外事项及验收条件以实施规格为准。
