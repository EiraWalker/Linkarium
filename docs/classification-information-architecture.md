# AI 个人书签分类：信息架构与知识组织的证据和执行协议

核查日期：2026-10-10（Asia/Taipei）。范围：信息架构、知识组织及其对个人书签库的适用边界。本次只检索公开资料并撰写本文，没有调用用户 AI API、修改数据库或编辑技能。下面将已核查的公开来源事实与项目建议分开。

## 结论

好的分类应让用户**能预判入口、能找回资源、能理解边界，并能长期维护**。目录数量少、每个目录数量平均、模型能输出合法 JSON，都不能单独证明分类质量。建议先从实际内容与用户的使用目的归纳候选结构，再以找回任务验证；只在结构获认可后，让 AI 依据同一份有定义的词表分批归类。这个执行顺序是本文综合建议，而不是某个标准指定的唯一流程。

## 目录要回答哪一个问题

以下是项目设计判断，不是统一适用于所有人的分类法。

先选定主导航的优先问题，随后才确定名字：

- **主题优先：** “我要找游戏、金融还是数学的资料？”适用于用户先想到领域、再想到具体用途的习惯。
- **用途优先：** “我要学习、拿素材、分析市场还是使用工具？”适用于围绕工作任务找资源的习惯。
- **有限的分层组合：** 第一层按用途、第二层按主题，或相反；必须明确每一层采用的判断轴，不能同级随意混用课程、AI、金融、Coursera和工具。

Obsidian 中的用途目录是一个有价值的候选；它不是已经通过书签找回测试的答案。反过来，也不应禁止所有“课程”或“平台”目录：若用户的真实任务是回到某校课程主页或管理某平台账号，形式/平台可能就是有用入口。问题在于有没有清楚的范围和找回理由，不是某类词在所有情况下都不准出现。

对于多义资源，应先记录“主用途/主主题/资源类型/适用工具/平台/处理状态”等独立属性，再决定哪些属性进入主目录，哪些做标签。主目录单归属是本项目约束；其余信息不应丢弃。例如开发教程可以归学习主题，同时用引擎、语言和课程形式补充检索；不能为了单归属把它的其他属性删掉。

## 为什么不能照搬参考截图或 Obsidian

1. **参考只覆盖部分内容。** 笔记库会偏向长期整理的知识，书签还包含账号页、交易工具、服务商、新闻入口和临时资源；参考树没有的领域可能在书签库里占有实质规模。
2. **目录是历史产物。** 旧目录也可能保留迁移残留和暂存习惯；截图只能显示名称、局部层次与数量，看不到每类边界和用户的找回行为。
3. **固定根会形成强制映射。** 当目录缺少数学统计或发布运营时，模型可能把这些资源放进“软件工程”或“通用工具”；字符串更统一，语义仍然不合格。
4. **目录均衡不是目标。** 一个长期高价值主题可以暂时只有一站；一个真实的大领域也可能有很多站。只为消除单例或平均数量而合并，会破坏语义。
5. **相似词不等于相同用途。** AI 字样可以出现在模型课程、营销产品和图像工具中；视频、书籍、博客、课程是载体；站点平台相同也可能讨论不同主题。

本地分类质量审计与真实收藏案例保留在使用者自己的数据中，不随源码发布。已经参与规则修订的案例应标记为已知回归案例，不再称为未见测试集。

## 可执行的归纳与分类协议

以下各步是面向当前个人书签规模的建议，步骤中的工作量不是通用标准规定的阈值。

### 1. 清点与证据分级

对资源保留独立 ID、原收藏标题、用户标题、当前页面标题、域名、有效摘要、原路径、已有手工标签和抓取状态。区别正常正文、缺正文、验证码、登录页、维护跳转、内容迁移。历史文件夹只作弱线索；无法读取页面不代表原标题也无价值，抓取成功也不代表得到可信正文。

产物是内容清单与质量问题表，不是分类结果。涉及登录/验证码的正文不能被当成实际业务主题；原始证据不被低质量抓取结果覆盖。

### 2. 从内容归纳候选，最后命名

抽取覆盖主要领域、稀有主题、常用资源、跨领域资源和弱证据页面的一组代表记录。第一遍不展示预设根，记录自然分组和难分项；第二遍再与参考目录对照，列出复用、改名、拆分、缺失类别的理由。

AI 可承担整理候选的工作，但应明确这是模型假设。随后让用户只处理少量真正决定结构的分歧，而不是逐站回答无效问题。个人库无须照搬面向多人研究的招募规模。

### 3. 对比一到两棵候选树

优先比较“主题优先”和“用途优先”中符合用户习惯的方案。每个候选节点提供：稳定 ID、中文显示名、别名、范围、纳入/排除条件、边界判定，以及少量示例。

先给出可审阅的目录预期和代表归属，再编写整库分类提示词。所有分类目录数量和层级都必须能解释为检索需要，而不是为达到固定的几个根、几十个叶子而凑数。

### 4. 做实际找回验证

用自然任务测试候选目录，不在任务里泄露目标分类名。例如“找到能比较同类产品市场表现的页面”“找一个学习随机过程的资料”“取一个可直接使用的音效资源”。记录第一步选哪类、是否到达合理结果、回退和犹豫。

先检查本人最常做的任务；再覆盖领域边界、同题不同载体及陌生资源。完成率、耗时只与本人旧方案和重复任务条件比较。树测试之后还要检查真实产品的搜索与标签找回；不要把一次树测试当作完整 UI 验收。

### 5. 固定词表后再进行批量分类

使用同一版本的类别 ID 和定义。每项输出主类别、辅助标签、简短可核查理由、所用证据、是否需要人工判断；模型不得在每个小批次偷偷更名或另建同义类别。新主题、边界冲突、低质量证据进入候选调整队列。

分批完成后检查跨批一致性，特别是同题名变体、同产品不同域名、同资源的多语言入口。校验 JSON 和合法 ID 是最低门槛，语义判断与找回效果必须单独检查。

### 6. 将验证分成三类

| 检查集 | 用途 | 不能声称的结论 |
| --- | --- | --- |
| 已知失败/边界案例 | 确认以前发现的问题不再出现；调规则可直接用它们 | 这些案例若已进入提示词或词表设计，就不是独立 holdout |
| 新抽取、预先人工标注的保留样本 | 不给模型答案，用于比较候选提示词与分类版本 | 小样本的比例不是全库或未来数据的保证 |
| 本人的真实找回任务 | 验证分类对使用者是否可预测、好找 | 不代表其他人也认同这棵树 |

已经参与规则设计和诊断的案例只能作为第一类。应另从未参与设计的资源中抽取保留样本，且避免用同一内容的另一个 URL 冒充独立样本。可以允许多个合理目的地，但必须在跑分类前说明可接受范围，不能事后为了让模型通过而放宽答案。

### 7. 通过增量维护保持稳定

新导入优先复用已有规范概念；“没有合适类别”进入待议，积累到有明确主题和找回需求时再决定增设。用户校对记录应区分错误归属、命名不清、证据不足和新主题，不能把一次移动一概当成永久硬规则。

每次目录变更记录版本、原因、受影响资源、旧 ID 到新 ID 的映射；同义合并尽量保留检索别名。重新分类只覆盖受定义变化影响的资源，或由用户明确选择整库重跑。定期抽查常用任务与未决队列，触发依据是实际错误或内容变化，不是每周随机重组一次。

## 最小验收条件

- 每个主类别有明确范围；同级没有未经说明的轴混用和同义重复。
- 真实主要领域有合理去处；无证据的条目允许待确认，不靠强制分配伪造覆盖率。
- 同内容或同用途变体跨批一致；用户的明确修正被保留并可追溯。
- 高频找回任务相对旧结构更直接；如果更漂亮却更难找，方案不通过。
- 输出包含可核查证据；仅有自报置信分数不算验证。
- 本轮新增范围、旧数据迁移和执行授权分别清楚；目录方案获认可前不启动整库 API 分类。

本文件是研究与建议交付。未宣称某套根目录已得到用户确认，也未宣称新的分类流程已经部署。
