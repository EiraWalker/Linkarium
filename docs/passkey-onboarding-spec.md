# Passkey 首次初始化、多凭据管理与跨设备登录

状态：需求及测试边界已确认，待实现。

## Problem Statement

Linkarium 的新安装目前必须先在服务器端提供私钥文件并创建所有者，浏览器才能注册 Passkey。未初始化的登录页只有终端操作提示，用户无法直接通过网页完成首次配置。私钥文件成为必选前提，与用户希望直接使用 Windows Hello、手机或安全密钥登录的需求不符。

现有设置页已经可以保存和列出多个 Passkey，但缺少重命名、删除以及未登录的新设备加入流程。现有会话没有关联具体登录凭据，单独删除凭据不能使已经登录的会话失效。电脑和手机需要通过同一个 HTTPS 地址跨网络访问，并能独立完成登录和添加凭据。

本功能继续使用单一所有者管理个人收藏库，不引入多用户账号或公开注册。

## Solution

提供网页首次初始化界面及完整的“登录与 Passkey”设置界面。新安装启动后，由服务器终端提供一次性初始化码；用户在网页输入该码并创建首个 Passkey，随后直接进入收藏库。首次配置不要求私钥文件、密码、邮箱或用户名。

已有用户可在当前已登录设备直接添加 Passkey，也可以生成一次性链接、二维码和独立授权码，让另一台电脑或手机添加自己的 Passkey。链接及二维码不包含授权码；新设备必须另行输入授权码。新设备授权自签发起五分钟有效，成功注册一次后失效。新电脑可复制链接到浏览器，手机可扫码，两种入口进入同一个添加流程。

设置页按 Passkey 凭据列出记录，支持命名、重命名、删除、创建时间和最后使用时间。删除某把 Passkey 后，使用它登录的全部会话失效。网页不得删除最后一种可用的登录凭据。

登录默认保持十四天，关闭浏览器后仍保留会话；十四天后重新登录。管理凭据和生成新设备授权不增加额外的身份复验弹窗。

失去全部登录方式时，用户从服务器终端发起重置，再在网页创建新 Passkey。新 Passkey 注册成功后，全部旧 Passkey、旧私钥文件登录凭据及旧会话失效，收藏库内容保留。私钥文件登录继续作为可选方式。

### 用户流程

| 场景 | 前提与操作 | 成功结果 |
| --- | --- | --- |
| 首次初始化 | 尚无所有者；输入终端初始化码，命名并创建 Passkey | 建立唯一所有者和首个凭据，直接登录，关闭首次初始化入口 |
| 在本机添加 | 已通过 Passkey 或私钥文件登录；点击“在本机添加 Passkey”并完成系统注册 | 添加一条凭据，保留当前会话，不要求授权码或额外身份复验 |
| 添加其他设备 | 已登录设备生成链接、二维码和独立授权码；新设备打开入口并输入码 | 新设备完成系统注册后直接登录，授权被一次性消费 |
| 日常登录 | 使用当前站点已登记的 Passkey，或可选的私钥文件 | 建立十四天会话 |
| 删除 Passkey | 设置中删除一条记录，且仍有其他可用登录凭据 | 该凭据及其会话失效；若当前会话使用它，当前页面退出 |
| 终端重置 | 管理员在服务器终端签发重置授权，用户在网页创建新 Passkey | 新凭据生效，所有旧凭据与旧会话失效，当前重置设备以新凭据登录 |

## User Stories

1. 作为首次部署者，我希望不准备私钥文件也能启动网站，以便直接在网页配置 Passkey。
2. 作为首次访问者，我希望未初始化的网站显示明确的配置入口，以便知道下一步要做什么。
3. 作为服务器管理者，我希望只有持有终端初始化码的人能建立所有者，以便控制首次访问授权。
4. 作为首次配置者，我希望不填写用户名、邮箱或登录密码，以便只完成个人收藏库需要的配置。
5. 作为 Windows 用户，我希望通过系统提供的 Windows Hello 或其他可用认证器创建 Passkey，以便使用本机的认证方式。
6. 作为手机用户，我希望用手机浏览器完成初始化、注册和登录，以便独立使用网站。
7. 作为跨网络使用者，我希望电脑和手机使用同一个 HTTPS 网站地址，以便在不同网络访问同一收藏库。
8. 作为首次配置者，我希望首个 Passkey 成功后直接进入收藏库，以便无需重复登录。
9. 作为配置中断的用户，我希望取消、断网或失败后仍能重新进行未完成的初始化，以便不会得到一个没有可用凭据的账号。
10. 作为已有用户，我希望升级后保留现有收藏和登录凭据，以便继续使用原来的收藏库。
11. 作为仅配置过私钥文件的用户，我希望先用原私钥登录，再添加首个 Passkey，以便平滑采用新的登录方式。
12. 作为已登录用户，我希望在当前设备直接添加 Passkey，以便无需为本机添加操作输入授权码。
13. 作为多设备用户，我希望一个所有者能登记多把 Passkey，以便不同设备可以独立登录。
14. 作为已登录用户，我希望生成供其他设备使用的链接和二维码，以便授权新设备加入。
15. 作为添加新电脑的用户，我希望复制链接并在新电脑浏览器打开，以便不依赖电脑摄像头扫码。
16. 作为添加手机的用户，我希望扫描二维码打开同一个配置入口，以便减少输入网址的操作。
17. 作为授权者，我希望页面另外提供一个授权码，以便新设备必须同时取得链接和授权码才能添加 Passkey。
18. 作为新设备用户，我希望输入授权码后命名并创建自己的 Passkey，以便以后直接登录。
19. 作为授权者，我希望新设备授权只有五分钟有效并且只可成功使用一次，以便限制授权的使用范围。
20. 作为使用过期入口的用户，我希望看到重新获取授权的提示，以便回到已登录设备生成新的入口。
21. 作为新设备用户，我希望注册成功后直接登录，以便立即使用收藏库。
22. 作为用户，我希望生成授权、添加和删除 Passkey 不增加额外身份复验步骤，以便操作保持简洁。
23. 作为用户，我希望为 Passkey 命名和重命名，以便区分办公电脑、手机认证器或密码管理器中的凭据。
24. 作为用户，我希望查看每把 Passkey 的创建时间和最后使用时间，以便判断其用途和使用情况。
25. 作为用户，我希望删除不再使用的 Passkey，以便它不能继续登录网站。
26. 作为用户，我希望删除凭据同时结束由它建立的全部会话，以便旧登录不会绕过撤销结果。
27. 作为用户，我希望删除当前登录凭据时立即退出当前页面，以便界面与服务端状态一致。
28. 作为用户，我希望删除一把 Passkey 不影响由其他有效凭据建立的会话，以便其他登录继续使用。
29. 作为用户，我希望网站阻止删除最后一种可用登录凭据，以便不会在网页操作中意外失去访问方式。
30. 作为使用同步 Passkey 的用户，我希望列表明确管理的是凭据，以便理解删除一条记录会影响所有使用同一凭据的设备。
31. 作为日常用户，我希望关闭浏览器后保持登录，并在登录满十四天后重新验证，以便兼顾持续使用与明确的有效期。
32. 作为主动退出的用户，我希望当前会话立即失效，以便该浏览器不能继续访问收藏库。
33. 作为失去全部登录方式的用户，我希望从服务器终端发起重置，以便无需邮箱或预先下载恢复文件也能恢复访问。
34. 作为发起重置的用户，我希望新 Passkey 成功后全部旧 Passkey、旧文件密钥凭据和旧会话失效，以便完成彻底的认证重置。
35. 作为收藏库所有者，我希望认证初始化和重置不删除网站收藏、收藏文件夹、标签、备注、页面快照或其他业务数据，以便身份操作与收藏内容分开。
36. 作为选择私钥文件的用户，我希望保留该登录方式，同时不强迫其他用户配置它，以便自行选择登录工具。
37. 作为遇到浏览器不支持或认证器取消的用户，我希望看到准确、可继续操作的错误提示，以便切换支持的环境或重新尝试。
38. 作为维护者，我希望用隔离收藏库验证全部流程，并分别记录自动化和实机结果，以便不会把模拟通过当成真实电脑和手机已验收。

## Implementation Decisions

以下区分用户确认的产品规则，以及为形成可实施规格而补齐的技术约定。新增实现沿用现有 Preact 前端、Django 认证与会话、WebAuthn 库及运行状态数据库，不新增独立账号服务。

### 1. 身份与初始化状态

- 继续采用单一所有者模型；首次初始化用于创建唯一所有者，不是开放账号注册。
- 将“准备数据目录、数据库迁移及运行单例”与“创建所有者及登记首个凭据”分开。纯新安装必须能先运行网页初始化界面；安装及启动流程不能再以私钥文件为必选参数。
- 首次初始化仅在尚无所有者时开放。已有所有者但没有 Passkey 的安装属于已有账号；零 Passkey、凭据损坏或丢失均不得自动重新开放匿名初始化。
- 终端初始化码只授权首次建立所有者。前端提交该码后才能获取注册授权，匿名访问页面或点击按钮本身不产生所有者。
- 首个凭据验证成功、所有者建立、凭据登记及初始化授权消费须在运行状态数据库中的一个提交边界完成。取消或失败不能留下新建但没有可用凭据的所有者。
- 两个浏览器并发初始化最多一个成功；首次初始化成功后，其余初始化授权不能再创建或替换所有者。

### 2. 授权类型与有效期

| 授权类型 | 签发方 | 接收端要求 | 有效期 | 成功后的作用 |
| --- | --- | --- | --- | --- |
| 首次初始化 | 尚无所有者时的服务器终端 | 输入初始化码并完成首个 Passkey 注册 | 成功使用前不过期；重启保留，手动重发替换旧码 | 建立所有者并关闭初始化入口 |
| 新设备添加 | 已通过 Passkey 或私钥登录的所有者 | 同时持有授权链接与独立授权码 | 五分钟，用户确认 | 只增加一把 Passkey，并登录新设备 |
| 终端重置 | 服务器终端管理员 | 输入重置授权并完成新 Passkey 注册 | 十分钟，技术默认，沿用现有控制台授权时长 | 撤销全部旧凭据和旧会话，并启用新凭据 |

- 三种用途独立验证，不能互相代用。未登录者不能签发新设备授权；新设备添加不能提升成终端重置。
- 新设备五分钟期限从签发时起计算，不因打开页面、验证授权码或刷新而延长。注册最终提交时仍必须在有效期内；注册 challenge 的有效期不得超过对应授权的截止时间。
- 所有授权只能成功消费一次。普通页面访问不消费授权；成功注册与消费必须原子提交，重放和并发提交不能登记多把凭据。
- 不提供待使用授权列表、状态查询页面、取消授权按钮或手动撤回操作。重新生成新设备授权不自动使旧授权失效；每条授权独立到期或在成功使用后失效。
- 过期的首次或重置授权从终端重新获取；过期的新设备授权从已登录设备重新生成。

### 3. 新设备链接、二维码与授权码

- “添加其他设备”一次返回一个高熵随机链接标识、同一链接的二维码、独立授权码和到期时间。
- 链接和二维码均不得包含授权码；授权码在发起设备单独显示，由用户在新设备手动输入。产品不自动发送邮件、短信或其他消息。
- 技术默认采用八位随机数字授权码，允许复制粘贴；每个授权最多五次错误输入，达到上限后该授权不可再使用。限流及错误次数必须由服务端控制，不把短期授权有效期当成防猜测措施。
- 链接标识与授权码仅在签发时展示原文；服务端只保存用于查找、比对和限流的派生值，不保存可直接取回的明文授权码。
- 授权与签发所有者、签发登录凭据、用途和站点身份关联。签发凭据被撤销或终端重置成功后，由旧凭据签发的未使用授权也不能再使用。
- 仅有链接、仅有授权码、错配的一组链接和码，以及已过期或已消费的组合，都不能完成登记。
- 授权码验证通过只获得本次注册能力，不直接获得收藏库访问会话。新 Passkey 验证成功后才登录。
- QR 生成在本地完成，不把授权链接提交给第三方二维码服务。授权秘密不进入普通业务日志、错误上报、埋点或来源地址；前端读取链接授权信息后清理不必要的地址栏与历史暴露。

### 4. 本机添加与凭据注册

- 已通过 Passkey 或私钥文件登录的所有者可以直接在本机添加，不输入新设备授权码；正常模式的有效会话就是该操作的授权前提。
- 不实现管理凭据前额外复验现有 Passkey／私钥的流程，也不实现“验证后五分钟免复验”的窗口。创建新 Passkey 时认证器本身要求的指纹、人脸或设备解锁属于注册过程。
- 复用现有 WebAuthn 注册／验证流程，要求用户验证，校验 challenge、会话、用途、RP ID、origin 和签名。不得以模拟签名或虚拟认证器作为实际用户登录凭据。
- 允许平台认证器、可用的密码管理器及安全密钥，不强制只使用某一种认证器或同步服务。
- 凭据名称沿用一至一百字的规则，允许用户自定义；名称不是实际硬件身份或安全验证结果。
- 同一凭据不得重复登记。现有凭据描述信息应正确传递已保存的 transport；不能因为同步凭据的签名计数或备份特征不同而自行加入与 WebAuthn 库不兼容的验证规则。
- 本机添加成功保持原会话的登录凭据关联和原到期时间；首次初始化、新设备添加和终端重置成功则使用新凭据建立新的登录会话。

### 5. Passkey 列表与删除

- 设置页展示名称、创建时间、最后使用时间，并提供本机添加、添加其他设备、重命名和删除入口。尚未用于认证的凭据以明确的未使用状态显示。
- 列表称为“Passkey”，不把一条凭据宣称为一台物理设备。用户可以自行命名为电脑、手机或密码管理器名称。
- 同步到多个设备的同一凭据仍是一条记录；删除该记录会影响所有使用它的设备。
- 删除前检查当前站点至少保留一种有效登录凭据：另一把可用 Passkey，或已登记、未撤销的文件密钥。不能以无效或其他站点不可用的记录通过检查。
- 删除与最后凭据检查必须具有并发保护，两个同时执行的删除操作不能各自通过检查后清空全部登录方式。
- 凭据删除和其会话撤销是一个对外可见的结果。已经登录的旧浏览器在下一次受保护请求时必须被拒绝，不能继续依靠十四天 cookie 使用网站。
- 删除当前会话的凭据后转到登录页；使用其他有效凭据的会话保持有效。已打开的静态页面无需被远程强制关闭，但不能继续取得受保护数据或执行操作。

### 6. 十四天会话与凭据关联

- 正常登录会话从本次登录成功时起固定十四天到期，使用持久 cookie；关闭浏览器不结束会话。普通浏览、页面刷新和添加凭据不滚动延长这个期限。
- 每个正常登录会话记录认证类型及实际登录凭据的稳定标识。后续受保护请求校验会话有效期、所有者状态和该凭据是否仍有效。
- 使用同步 Passkey 的多个浏览器可以建立不同会话，但关联同一凭据；删除该凭据使这些会话全部失效。
- 主动退出仅撤销当前会话；终端重置成功撤销全部旧会话。
- 升级前缺少凭据关联的会话无法可靠归属。技术迁移约定为这些旧会话要求一次重新登录，保留现有凭据及收藏数据，不猜测其凭据来源。
- 正常模式继续拒绝密码登录；现有调试模式不成为绕过正常授权、初始化或撤销规则的入口。

### 7. 服务器终端重置

- 提供与普通添加明确区分的终端重置操作；发起时不要求用户还持有任何旧 Passkey 或私钥文件。
- 签发重置授权本身不删除旧凭据。用户取消、网络失败、授权过期或新凭据验证失败时，旧认证状态和收藏数据保持原状。
- 新 Passkey 成功登记时，在同一运行状态事务内撤销此前全部 Passkey、全部文件密钥登记、旧会话及旧的未使用注册／重置授权，仅保留这次新凭据；之后为本次操作建立新会话。
- 并发的其他重置流程不得在第一次重置成功后继续凭旧授权重置新状态。
- 成功结果明确表示“旧登录凭据已撤销”。网站保证旧凭据无法再登录，不承诺远程删除 Windows、手机或密码管理器内的私钥，也不删除用户自行保存的私钥文件。
- 不生成要求用户预先下载的恢复凭据，不实现邮件、短信、恢复文件或客服找回。

### 8. 可选私钥与已有安装

- 私钥文件不是安装、首次网页初始化、Passkey 登录、本机添加或新设备加入的必要条件。
- 保留现有文件密钥登记及浏览器本地签名登录能力；服务器不接收私钥内容。已有文件密钥用户可以先登录，再直接添加 Passkey。
- 已有所有者和收藏库不进入首次初始化，也不能因为升级而重建、清空或替换现有凭据。
- 现有终端新增 Passkey 的入口若保留，必须清楚标识为“新增”，并复用新设备授权规则，不能保留一个绕过独立授权码的普通新增入口；它不能隐式执行终端重置。
- 本次不扩大为私钥文件的完整网页管理器。终端重置仍须撤销所有已登记文件密钥。

### 9. 模块、接口及数据边界

- 前端登录模块承载首次初始化、日常登录、接收新设备授权和接收终端重置授权；设置模块承载 Passkey 列表及管理入口。
- 后端认证模块负责授权签发与验证、WebAuthn 验证、凭据登记和撤销；会话校验模块负责十四天期限与凭据关联；部署及管理命令负责无私钥启动、初始化授权和终端重置。
- 复用现有 session 状态、Passkey 注册／登录 options 与 verify、凭据列表接口。补齐首次状态、授权签发与授权码验证、凭据重命名和删除能力；API 返回明确的未初始化、未登录、授权无效／过期、不可删除最后凭据等结果。
- 未登录客户端只可读取配置流程所需的最少状态并提交其授权，不得读取凭据列表或收藏数据。
- 凭据、授权及凭据与会话关联放在运行状态数据库；收藏、文件夹、标签、备注、快照和业务任务继续放在收藏库数据库。沿用运行身份与可恢复收藏库分离的架构，不增加跨库外键。
- 认证重置不得改动收藏库 generation 或业务内容；整库恢复不得把旧登录凭据重新恢复出来。
- 保留现有 CSRF、来源校验、同源访问和受保护资源鉴权。新增接口的错误、重放和并发处理必须在服务端执行。

### 10. HTTPS、电脑与手机

- 跨网络访问统一使用部署者配置的同一个可解析 HTTPS 地址，注册与登录遵循同一站点身份；支持电脑和手机分别直接访问。
- 配置和部署说明须覆盖正确的外部来源、可信代理及安全 cookie。实现不得把授权链接写死为服务器本机地址，也不得从不可信转发头构造外部链接。
- 本机开发地址仅用于开发验收。切换主机名不会自动迁移现有 Passkey；手机自己的 localhost 不能被当作另一台电脑的服务地址。
- 页面适配手机输入、粘贴、扫码后打开和系统认证交互；键盘及辅助技术可访问输入、按钮和状态消息。
- 对非安全上下文、不支持 WebAuthn、用户取消、授权过期及注册失败显示可操作的状态。浏览器能力不同不能导致悄悄开放密码或无授权注册。

### 11. 失败及重试

- 明确区分“认证器创建了凭据”和“网站验证并登记成功”；只有后者建立账号／新会话并消费授权。
- 同一成功提交发生网络重试时，不能重复登记或多次重置。应能查询当前会话／初始化结果以恢复正确页面状态，不把已成功处理的超时简单变成第二次注册。
- 如果网站未登记成功，则保持未初始化或未完成添加／重置状态，并提供重新尝试或重新获取授权的路径。系统密码管理器可能留下未登记条目，不能承诺服务端事务能撤回认证器上的生成操作。
- 失败提示只提供完成操作所需的信息，不展示签名、密钥、授权秘密或内部异常栈。

## Testing Decisions

用户已确认：以“真实浏览器＋隔离收藏库”的完整流程为主，复用认证 API 测试覆盖授权码、过期与撤销；真实 Windows Hello、手机和跨网络 HTTPS 另外进行实机验收。

### 测试边界与先例

- 主边界使用真实构建后的前端、实际 HTTP 服务、隔离运行数据及浏览器操作。优先扩展现有“隔离收藏库＋虚拟认证器”的认证浏览器验收，避免为每个组件建立独立测试缝隙。
- 复用现有 Django 认证请求测试：当前已有真实签名校验、challenge 到期与重放、来源／用户验证、CSRF、文件密钥登录和设置页添加等先例。新增错误、限流、并发及时间边界在同一认证 API 边界验证。
- 终端操作通过实际命令入口验证，不能用直接写数据库代替初始化、签发或重置动作。
- 好的测试断言用户看见的状态、请求结果、能否登录及受保护资源是否可访问；不以内部 helper 调用次数、私有方法名或 UI 实现结构作为主要验收。
- 数据库记录可作为补充证据，不能代替实际登录和会话撤销的外部验证。

### 必须通过的自动化验收

| 编号 | 场景与通过条件 |
| --- | --- |
| A01 | 全新隔离目录，无私钥文件；完成部署准备后服务可启动并显示首次初始化界面。 |
| A02 | 正确终端初始化码完成首个 Passkey 登记并直接登录；不要求用户名、邮箱、密码或私钥文件。 |

| A04 | 初始化取消、断网及验证失败不留下没有凭据的新所有者；成功响应丢失后的重试不重复创建。 |
| A05 | 已有文件密钥安装保留收藏与原登录能力，登录后可直接添加首个 Passkey；不会进入匿名初始化。 |
| A06 | 已登录设备直接添加多个 Passkey，不要求授权码、不弹出额外的旧凭据复验；原会话关联与期限不被改写。 |
| A07 | 同一添加入口同时提供可复制链接和可解码的二维码；二维码与链接均不包含独立授权码，也不使用第三方 QR 服务。 |

| A10 | 通过可控时间验证签发后五分钟边界；页面刷新或码验证不续期，截止时间后的最终提交被拒绝。 |
| A11 | 对同一授权并发提交最多登记一把凭据；失败或重试不能扩大授权次数。 |
| A12 | 重新生成授权不隐式撤销此前尚在有效期内的授权；页面不出现待授权列表、状态面板或撤回按钮。 |
| A13 | Passkey 可重命名，显示正确的创建和最后使用时间；同一凭据不重复登记。 |
| A14 | 删除凭据后，该凭据登录被拒绝，已有多个相关会话访问受保护 API 和资源均被拒绝。 |

| A17 | 相同凭据在多个独立会话中使用时，删除会同时撤销这些会话；不同凭据不受牵连。 |
| A18 | 会话 cookie 跨浏览器关闭保留；从登录成功起固定十四天到期；日常请求不续期；主动退出立即失效。 |
| A19 | 升级前无凭据归属的旧会话需要重新登录，但旧凭据和业务数据不变。 |

| A26 | 桌面和手机尺寸下输入、粘贴、命名、错误及成功页面可操作；非安全上下文、不支持能力和认证器取消有明确反馈。 |

### 实机验收与证据

- 在统一 HTTPS 测试站点，以真实 Windows Hello 或可用电脑认证器完成注册、退出和再次登录。
- 使用真实手机浏览器扫码、输入独立授权码、创建 Passkey、退出并再次登录；手机实际使用另一网络访问站点。
- 在另一台电脑通过复制链接完成加入并独立登录，证明“添加其他设备”不依赖摄像头。
- 在真实设备上验证删除凭据后的重新登录失败及旧会话失效；同步 Passkey 的结果应按共享凭据记录解释。
- 记录设备、系统、浏览器、认证器类型、访问来源、通过项与失败项。只对实际验收过的组合声明通过。
- 虚拟认证器证明浏览器与服务端协议路径，手机尺寸证明布局；二者都不能替代真实 Windows Hello、手机认证器和跨网络验收。缺少实机或可用 HTTPS 环境时，相关验收明确保持未完成。
- 所有自动化与重置验证使用隔离收藏库和测试凭据，不重置日常收藏库，不发布真实授权链接、授权码、凭据标识或个人截图。

## Out of Scope

- 多用户、公开注册、账号邀请、邮箱或用户名系统。
- 要求用户预先配置私钥文件，或下载并保存恢复凭据。
- 邮箱、短信、密码找回，以及正常模式的密码登录。
- 生成授权、增删凭据之前再次验证现有 Passkey／私钥，以及任何“最近验证五分钟”机制。
- 新设备授权状态列表、使用进度查询、手动取消／撤回、重新生成自动作废旧链接。
- 在已登录设备上直接添加 Passkey 时要求新设备授权码。
- 把一条 Passkey 记录视为一台真实物理设备，或实现独立的物理设备／登录会话管理面板。
- 远程删除用户设备、密码管理器或文件系统中的私钥。
- 私钥文件的完整网页管理器、自动发送授权邮件／短信，以及额外的发起设备二次审批。
- 在本规格编写阶段修改业务代码、重置现有账号、迁移真实凭据、执行实际公网部署、修改 DNS 或证书配置。

## Further Notes

- 本规格以最后确认的方案为准：新设备授权为五分钟，会话为十四天；早期讨论中的十分钟新设备链接、三十天会话、额外身份复验、授权撤回及恢复文件均已被后续决定替代。
- 用户后续确认首次初始化及已有所有者的首个 Passkey 授权码成功使用前不过期，服务重启保留；手动重新生成替换旧码。终端重置仍为十分钟，新设备仍为五分钟。八位授权码和五次错误上限保留。
- 本规格要求服务器撤销旧文件密钥登记，使旧私钥无法登录；“删除旧私钥”不表示能删除用户设备上的文件。
- 现有安装已支持多 Passkey 存储及设置页添加，实施时应复用并扩展，不能把这些能力重复实现成另一套认证系统。
- 已有早期密码认证文档与当前公私钥认证文档存在不同历史阶段；实施后更新安装、认证、部署和验收说明，以本规格的正常模式规则为准。
- 参考：[SimpleWebAuthn 的 Passkey 与同步凭据说明](https://simplewebauthn.dev/docs/advanced/passkeys)、[WebAuthn 对凭据更新通知的处理边界](https://www.w3.org/TR/webauthn-3/#sctn-signal-methods)。
