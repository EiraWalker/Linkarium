# 网站库加载速度优化

2026-10-16，用户授权继续优化加载速度。优化前重新采集当前 8001 服务，完成后使用同一网站库、同一批预览和相同浏览器流程复测。没有修改图片质量、收藏记录、快照历史、鉴权策略或数据库结构。

## 实现

- `frontend/src/features/previews/PreviewDocuments.ts`：JPEG 队列由桌面 2／手机 1 改为最多 6 张，保留首屏优先、整页加载、共享下载与会话缓存。所有锚点先读取位置，再集中更新预览；每个滚动容器的起点每次只测一次。
- `frontend/src/app/App.tsx`：后台任务目录的完成版本负责刷新网站库。取消“读取一个已完成历史任务就刷新全库”的重复触发；关闭任务弹窗时仅轮询摘要，打开时再获取整组任务明细。
- `backend/library/catalog.py`：目录数量由有收藏的目录沿祖先链累加，复用父目录关系，替代逐个目录反复扫描子树。
- `backend/library/queue.py` 与 API：通过数据库存在性查询排序并选择当前历史页，再汇总这页和当前活动批次的详细计数；当前任务摘要独立于历史页。分页结构、全部状态优先级、校对数量和完成版本不变，不缓存活动进度。
- `backend/library/preview_cache.py` 与 API：使用已读取的 `RuntimeState.active_generation` 定位图片，避免再次打开状态库。仍逐请求鉴权、检查版本存在性、校验安全路径和 ETag。

## 结果

`output/performance/load-optimization-20261016/report.html` 是可离线打开的图表报告。原始记录在其 `before/`、`after/`、`paired/` 子目录。

每场景 3 次，以下为首张图片请求发出到当前页全部可用预览解码就绪的中位数：

| 场景 | 优化前 | 优化后 | 耗时减少 |
| --- | ---: | ---: | ---: |
| 桌面首次加载 | 592.3 ms | 341.5 ms | 42.3% |
| 桌面再次加载 | 595.9 ms | 341.6 ms | 42.7% |
| 手机首次加载 | 786.3 ms | 418.3 ms | 46.8% |
| 手机再次加载 | 746.8 ms | 423.6 ms | 43.3% |

各次均为 48 张卡片、45 张已有快照。桌面图片编码总字节数均为 4,450,829，手机均为 2,158,251；不是减少加载图片数量或降低质量获得的提速。手机为 Chromium 视口模拟，不能当作真机结果。

12 次正式服务观测中，网站列表、目录、标签、设置和任务目录各从 24 次降至 12 次，整组任务明细从 30 次降至 0 次；弹窗打开与任务实时更新另行验收。较长的临时实例导航可以发生正常的两秒轮询，不能将所有额外任务列表请求都判为初始化重复。

CPU 在独立进程内交替运行 Git 基线和当前 GET 实现，避免比较前后相距较远的两个独立批次。三轮中位数中，目录约减少 64%，任务目录约减少 23%；图片因设备和 200／304 状态不同，约减少 0–24%。未改的网站列表也有约 18% 波动，不将其差值归为代码优化成果。原始样本全部保留。

4／6／8 并发使用相同请求拦截、新上下文、关闭 HTTP 缓存、轮换顺序，各测 3 次。6 张的速度与 CPU 组合较合适，未选择继续扩大并发。瞬时占用可能提高：正常手机首次加载样本的累计 Web CPU 增加约 26%；其余三场景的中位数约降低 9–12%。不宣称所有场景 CPU 都下降。

只重载 Web 子进程，原采集 worker PID 13240 及其启动时间保持不变。构建资源先暂存，再注册新静态资源并切换入口；发布后的页面与 JS/CSS 均验证 HTTP 200。没有提交新抓取、AI 分类、批准或修改真实收藏。
